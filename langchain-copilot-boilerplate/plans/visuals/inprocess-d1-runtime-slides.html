Why we changed it

v1 worked — but carried a whole second platform

  • Five processes to chat locally — web, agent, LangGraph server, Postgres, Redis (three of them in Docker)
  • Graph code was baked into a Docker image — every middleware change meant a rebuild, not a hot reload
  • State split across two engines — checkpoints in Postgres, transcripts in D1; delete had to chase both
  • An extra trust boundary to guard — :2024 trusted identity headers; anyone reaching it could impersonate anyone
  • Checkpoints only as durable as a local Docker volume

The solution in one line

Run the graph in our own process; put every byte of state in D1

What actually changed

Before → after

v1 — server-hosted graph
  • 5 processes — web · agent · langgraph · postgres · redis
  • 2 state engines — Postgres (checkpoints) + D1 (transcripts)
  • Graph changes → Docker image rebuild
  • Identity: headers forwarded over HTTP → copied into config by the server
  • Checkpoint durability = local Docker volume
  • Checkpoints not user-scoped — guessed thread UUID could attach
  • Runs via LangGraphAgent(deploymentUrl)
v2 — in-process graph
  • 3 processes — web · agent · memory worker (no Docker)
  • 1 durable store — D1 owns checkpoints, transcripts, titles, recall
  • Graph changes → tsx hot reload
  • Identity: verified once, injected into the run config in-process
  • Checkpoints survive restarts, redeploys, laptop swaps
  • Every checkpoint row scoped by user_id — cross-user reads return nothing
  • Runs via BuiltInAgent factory + our bridge

The gotcha we had to solve

One message, two ids

  • While streaming, a reply has a provisional id (run-…); the engine's final state assigns the real one (resp-…) — and that final id is what the durable transcript records
  • Without reconciliation, reopening a thread showed duplicate bubbles: the streamed copy and the hydrated copy of the same reply
  • Server side: every run ends with a MESSAGES_SNAPSHOT built from final engine state — summary and system messages filtered out, ids now match D1
  • Client side: the thread hydrator remembers every message it has seen, re-adds anything a snapshot dropped, and treats "same role + content, new id" as a rename, not a new message
  • Result: full history on screen, compact state in the engine, zero duplicates — proven in E2E across restarts

Persistence

everything durable is a D1 row

Where conversations live now

Three memory layers, one database

Checkpoint
Engine memory — full graph state per thread. Correctness-critical: a failed write fails the run, never silently forks a conversation. Survives restarts and redeploys.
D1 · checkpoints + checkpoint_writes
Transcript
Product ledger — every user/assistant turn with its engine message id. Sidebar, titles, rename, delete, semantic recall. Best-effort: an outage never breaks chat.
D1 · memory_turns + Vectorize
UI replay
CopilotKit's in-process run cache for instant re-render. Disposable — the hydrator rebuilds the screen from the transcript whenever it's gone.
runtime RAM
  • Summarization (16 messages trigger / keep 8) bounds the prompt; the transcript keeps everything — the UI never loses history to compaction
  • Deleting a thread wipes turns, checkpoints, and pending writes in one place

The new saver

Official schema, our store

  • Port of LangChain's official SQLite saver — same tables, same write semantics, plus a user_id column on everything
  • Serialization stays in the agent (real HumanMessage/AIMessage revival); the worker stores opaque base64
  • Writes are atomic via db.batch(); each put prunes to the latest 20 checkpoints per thread — no cron, no unbounded growth
  • No worker configured? Falls back to in-memory checkpoints with a warning — the boilerplate still runs
worker · 5 endpoints 
POST /v1/checkpoints/get-tuple
POST /v1/checkpoints/put          ← + prune keep-20
POST /v1/checkpoints/put-writes   ← atomic batch
POST /v1/checkpoints/list
POST /v1/checkpoints/delete-thread

-- every query:
WHERE user_id = ? AND thread_id = ?
-- wrong user → no rows → no leak

How failure is handled

Two stores, two failure philosophies

  • Checkpoints fail loud — a swallowed error would silently lose or fork conversation state, so saver errors fail the run and the user sees it
  • Transcript memory fails soft — retrieval degrades to empty, writes drop with a warning; a chat turn never dies because the ledger hiccuped
  • Identity is server-minted, end to end — verify → overwrite headers → per-request closure → run config → saver scope + tool headers. The model never chooses whose data it touches
  • Guardrails in the worker — 2 MB payload guard (D1's hard cap), key-validated metadata filters, Cloudflare Access on every deployed request
  • HITL door stays open — the bridge runs on the standard AG-UI interrupt protocol; approval flows are an add-on, not a rewrite
