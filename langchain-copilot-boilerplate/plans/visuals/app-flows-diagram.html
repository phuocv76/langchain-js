01 — System architecture

The browser never talks to the agent directly. Everything goes through Next.js server routes, which verify the Firebase session and forward a shared COPILOT_RUNTIME_SECRET plus the httpOnly session cookie. The agent re-verifies that cookie, then only sanitized x-agent-* identity headers travel onward to LangGraph.

02 — Sign-in flow

Google popup sign-in happens client-side, but the ID token is immediately exchanged for a server-minted, httpOnly session cookie (5-day expiry) — then the client signs out of the Firebase SDK. No Firebase credential ever persists in the browser.

03 — Authenticated chat request

Each hop strips what the next hop must not see: the proxy removes browser-supplied identity headers and adds the runtime secret; the agent verifies the cookie again (with revocation), deletes it, and emits sanitized x-agent-request-id / user-id / tenant-id / roles headers. The CopilotKit runtime forwards only that allowlist to LangGraph.

Gotcha from the code review: the agent rejects sessions missing the tenant_id and roles Firebase custom claims with a 403 (agent-user-auth.ts). A fresh Firebase project has neither, so chat fails after login until claims are set via the Admin SDK.

04 — Durable memory pipeline

durableMemoryMiddleware wraps the ReAct loop: before the model runs it retrieves same-tenant, same-user context and persists the incoming user turn (so a failed run still keeps the question); after the run it persists the assistant turn. The Cloudflare worker chunks each turn to 800 chars, embeds with bge-base-en-v1.5, and upserts into Vectorize.

Resilience note: memory-worker calls have no timeout and throw on failure inside beforeAgent / afterAgent — if the worker is down or hanging, chat runs fail or stall. Summarization (trigger 16 messages, keep 8) bounds the live prompt independently.
